# 自动化任务设计方案

## 目标

基于可逆计算原理，为 Yushi Agent 系统添加自动化执行能力。通过统一的规则引擎（RuleEngine）支持两种触发方式：

1. **时间驱动**：基于 cron 表达式的周期性任务（如"每天早上8点汇报天气"）
2. **事件驱动**：基于外部数据流的条件触发（如"温度超过85度时报警"）

核心洞察：**时间本身就是一种事件源**。将"时钟"视为内建事件源，cron 表达式就只是对时间字段的条件匹配操作符（`cron-match`）。

## 核心概念

### 事件源（EventSource）

事件源定义数据的来源。系统内建 `clock` 时钟事件源，用户可配置外部数据源：

```xml
<EventSources>
    <!-- 内建：系统自动注册，不需要用户配置 -->
    <source id="clock" name="系统时钟" type="internal" />
    
    <!-- 用户配置的外部数据源 -->
    <source id="string" name="string" type="enum::mqtt,http,file,internal"
            endpoint="string" topic="string" format="enum::json,csv,text"
            poll-interval-ms="!long" />
</EventSources>
```

**属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| id | string | 事件源唯一标识 |
| name | string | 事件源名称 |
| type | enum | 类型：mqtt/http/file/internal |
| endpoint | string | 连接端点（MQTT broker/HTTP URL/文件路径） |
| topic | string | 主题（MQTT topic/HTTP path） |
| format | enum | 数据格式：json/csv/text |
| poll-interval-ms | !long | 轮询间隔（HTTP/file 类型使用） |

### 规则（Rule）

规则是统一的触发单元，同时表达定时任务和事件触发。采用**属性优先**的最小信息表达：

```xml
<Rules>
    <rule id="string" name="string" description="string"
          enabled="boolean" source-id="string"
          match="enum::all,any" window-seconds="int"
          capture-pre-seconds="int"
          message="string" timeout-seconds="int"
          last-run-at-ms="!long" last-status="enum::ok,error,skipped" last-error="string">
        <condition field="string" op="enum::gt,lt,gte,lte,eq,ne,contains,cron-match"
                   value="string" duration-seconds="int" />
        <!-- group: 逻辑组合器，支持递归嵌套（推荐深度 ≤ 2-3 层） -->
        <group match="enum::all,any">
            <condition />  <!-- 引用上面的 condition 定义 -->
            <group />      <!-- 递归嵌套 -->
        </group>
    </rule>
</Rules>
```

**规则属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| id | string | 规则唯一标识 |
| name | string | 规则名称 |
| description | string | 规则描述 |
| enabled | boolean | 是否启用 |
| source-id | string | 关联的事件源 ID（clock 表示时间驱动） |
| match | enum | 顶层条件匹配模式：all（AND）/any（OR），控制顶层 condition 和 group 之间的逻辑关系 |
| window-seconds | int | 时间窗口大小（秒），条件必须在此窗口内同时满足 |
| capture-pre-seconds | int | 触发时捕获前 N 秒的数据 |
| message | string | 触发执行的消息/指令 |
| timeout-seconds | int | 执行超时秒数 |
| last-run-at-ms | !long | 上次执行时间戳 |
| last-status | enum | 上次执行状态 |
| last-error | string | 上次错误信息 |

**条件属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| field | string | 数据字段路径（如 `temperature`、`time`） |
| op | enum | 操作符：gt/lt/gte/lte/eq/ne/contains/cron-match |
| value | string | 比较值（cron-match 时为 cron 表达式） |
| duration-seconds | int | 持续时间要求：条件必须连续满足指定秒数才算成立 |

**条件组属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| match | enum | 组内条件匹配模式：all（AND）/any（OR） |

> **设计说明**：`<group>` 是逻辑组合器，可包含 `<condition>` 和嵌套的 `<group>`。推荐嵌套深度不超过 2-3 层，实际场景几乎不需要更深的嵌套。

**关键设计**：

- `cron-match` 是专用于时间匹配的操作符，value 为标准 cron 表达式
- `source-id="clock"` + `op="cron-match"` = 纯时间驱动规则
- 非 clock 源 + `op="cron-match"` = 时间过滤器（混合条件）
- 只有 `<condition>` 列表和 `<group>` 用子元素（因为数量不定），其他均为属性
- `<group>` 支持条件嵌套，可表达任意复杂的 AND/OR 组合逻辑

**LLM 友好性设计**：

条件模型的设计优先考虑 LLM 的理解和生成能力，这是区别于传统规则引擎（如 Nop rule.xdef）的核心优势：

| 设计选择 | 说明 |
|---------|------|
| **清晰的语义分离** | `<condition>` 是叶子谓词（判断），`<group>` 是逻辑组合器（AND/OR）。语义明确，LLM 无需学习复杂的递归决策树结构 |
| **零学习成本** | 自然语言描述直接映射：`"温度>85 且 (振动>0.2 或 压力>100)"` → 一个 condition + 一个 any group |
| **扁平优先** | 简单场景（纯 AND 或纯 OR）保持平面结构，rule 的 match 属性作为顶层逻辑，向后兼容 |
| **深度限制** | 推荐嵌套深度 ≤ 2-3 层。实际业务场景几乎不需要更深的嵌套，过深的嵌套反而说明规则需要拆分 |

**对比 Nop 式递归决策树**：Nop 的 rule.xdef 使用统一的递归 `<children>` 结构表达决策树，虽然理论上更通用，但对 LLM 不友好——需要理解"节点既是条件又是组合器"的复杂语义。Yushi 的 condition/group 分离设计牺牲了一点点通用性，换取了显著的 LLM 可用性。

### 执行器（Executor）

执行器是规则触发后的执行基础设施，负责调用 `jieyusha::chat()` 执行 LLM 驱动的任务：

```rust
/// 任务执行请求
struct ExecutionRequest {
    /// 执行来源标识（用于生成 session 目录）
    source_id: String,
    /// 要执行的消息/指令
    message: String,
    /// 超时秒数
    timeout_seconds: u32,
    /// 附加上下文（事件数据、触发时间等）
    context: Option<String>,
}

/// 任务执行结果
struct ExecutionResult {
    status: ExecutionStatus,  // ok | error | timeout
    error: Option<String>,
    started_at: i64,
    finished_at: i64,
}
```

执行器的职责：
- 创建独立的 history 目录：`automation/sessions/{rule_id}_{timestamp}/`
- 调用 `jieyusha::chat()` 执行 message
- 管理超时控制
- 记录执行结果

### 隔离执行

自动化任务在**独立的 Agent 会话**中执行，不干扰主会话：

```
┌─────────────────────────────────────────────────────────┐
│                    主会话 (Main Session)                 │
│  history/                                               │
│  ├── 0_workspace.xml                                    │
│  ├── 1_intent.xml     ← 用户交互                        │
│  └── ...                                                │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│             自动化任务会话 (Automation Session)           │
│  automation/sessions/{rule_id}_{timestamp}/             │
│  ├── 0_workspace.xml                                    │
│  ├── 1_intent.xml     ← message 或 task 作为 intent     │
│  └── ...                                                │
└─────────────────────────────────────────────────────────┘
```

## RuleEngine 设计

### 架构概览

RuleEngine 是统一的规则引擎，整合了时间驱动和事件驱动的触发能力：

```
EventSources（含内建 clock）
       │
       │  数据流
       ▼
  RuleEngine（统一）
   ├── 条件匹配器（含 cron-match 操作符）
   ├── 窗口评估器（滑动窗口 + 持续时间）
   └── 环形缓冲区（回溯数据）
       │
       │  触发
       ▼
   Executor → jieyusha::chat()
```

### cron-match 优化

对于 `source-id="clock"` 的规则，不能每秒触发规则评估（太浪费）。RuleEngine 采用**预计算下次匹配时间**的优化策略：

```rust
/// 时钟规则的下次触发时间
struct ClockRuleState {
    rule_id: String,
    next_match_at_ms: i64,  // 预计算的下次匹配时间
}
```

优化策略：
1. 对于 `source-id="clock"` 的规则，解析 cron 表达式预计算下次匹配时间
2. 使用单定时器 sleep 到最近的下次匹配时间
3. 触发后重新计算下次匹配时间
4. 对于非 clock 源，才是实时数据流评估

### 核心循环

```rust
/// RuleEngine 命令
enum RuleCommand {
    Add(Rule),
    Update(String, RulePatch),
    Remove(String),
    RunNow(String),
    Shutdown,
}

/// RuleEngine 核心循环
loop {
    tokio::select! {
        // 分支1：时钟规则到期
        _ = sleep_until(next_clock_wake) => {
            execute_due_clock_rules().await;
            recompute_next_clock_wake();
        }
        // 分支2：收到外部事件数据
        Some(event) = event_rx.recv() => {
            evaluate_event_rules(&event).await;
        }
        // 分支3：收到管理命令
        Some(cmd) = command_rx.recv() => {
            handle_command(cmd).await;
        }
    }
}
```

### 规则评估

```rust
/// 事件数据点
struct EventData {
    source_id: String,
    timestamp_ms: i64,
    fields: HashMap<String, Value>,
}

/// 规则状态机
struct RuleState {
    rule_id: String,
    /// 每个条件的持续满足开始时间
    condition_start_times: Vec<Option<i64>>,
    /// 上次触发时间（用于防抖）
    last_triggered_at: Option<i64>,
}

/// 环形缓冲区
struct RingBuffer {
    data: VecDeque<EventData>,
    max_duration_ms: i64,
}
```

规则评估伪代码：

```rust
fn evaluate_rule(rule: &Rule, data: &EventData, state: &mut RuleState) -> bool {
    let now = data.timestamp_ms;
    let mut satisfied_count = 0;
    
    for (i, cond) in rule.conditions.iter().enumerate() {
        let is_satisfied = match cond.op {
            Op::Gt => data.fields.get(&cond.field) > cond.value,
            Op::Lt => data.fields.get(&cond.field) < cond.value,
            Op::CronMatch => {
                // 对于非 clock 源的 cron-match，检查当前时间是否匹配
                let current_time = Utc::now();
                cron_matches(&cond.value, current_time)
            }
            // ... 其他操作符
        };
        
        if is_satisfied {
            // 记录条件开始满足的时间
            if state.condition_start_times[i].is_none() {
                state.condition_start_times[i] = Some(now);
            }
            
            // 检查是否满足持续时间要求
            if let Some(duration) = cond.duration_seconds {
                let start = state.condition_start_times[i].unwrap();
                if (now - start) >= duration * 1000 {
                    satisfied_count += 1;
                }
            } else {
                satisfied_count += 1;
            }
        } else {
            // 条件不满足，重置计时器
            state.condition_start_times[i] = None;
        }
    }
    
    match rule.match_mode {
        Match::All => satisfied_count == rule.conditions.len(),
        Match::Any => satisfied_count > 0,
    }
}
```

## RuleTool 工具设计

统一的规则管理工具，取代原来的 CronTool + EventRuleTool：

```xml
<tool name="Rule" description="管理自动化规则：创建、查看、更新、删除规则，支持时间驱动和事件驱动"
      input-schema="{...}" />
```

**操作说明**：

| 操作 | 说明 |
|------|------|
| status | 查看引擎状态（规则总数、下次时钟触发时间、活跃事件源数量） |
| list | 列出所有规则 |
| add | 创建规则 |
| update | 更新规则属性 |
| remove | 删除规则 |
| run | 立即触发规则执行（不影响正常调度） |
| list-sources | 列出可用事件源 |

**参数说明**（JSON Schema）：

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| action | enum | 是 | 操作类型：status/list/add/update/remove/run/list-sources |
| id | string | update/remove/run 时必需 | 规则 ID |
| name | string | add 时必需 | 规则名称 |
| description | string | 否 | 规则描述 |
| source_id | string | add 时必需 | 事件源 ID（clock 表示时间驱动） |
| match | enum | 否 | 顶层匹配模式：all/any，默认 all |
| window_seconds | integer | 否 | 时间窗口秒数 |
| capture_pre_seconds | integer | 否 | 捕获触发前数据的秒数 |
| conditions | array | add 时必需 | 顶层条件列表 |
| groups | array | 否 | 顶层条件组列表（用于混合 AND/OR 逻辑） |
| message | string | add 时必需 | 触发时执行的消息 |
| timeout_seconds | integer | 否 | 超时秒数，默认 300 |
| enabled | boolean | 否 | 是否启用，默认 true |

**conditions 数组元素**：

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| field | string | 是 | 数据字段路径（时间驱动固定为 `time`） |
| op | enum | 是 | 操作符：gt/lt/gte/lte/eq/ne/contains/cron-match |
| value | string | 是 | 比较值（cron-match 时为 cron 表达式） |
| duration_seconds | integer | 否 | 持续时间要求 |

**groups 数组元素**：

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| match | enum | 是 | 组内匹配模式：all/any |
| conditions | array | 否 | 组内条件列表 |
| groups | array | 否 | 嵌套的条件组（支持递归，推荐深度 ≤ 2-3 层） |

## 持久化存储

### 存储路径

```
{root_path}/
├── automation/
│   ├── sources.xml     # 事件源配置
│   ├── rules.xml       # 规则持久化（统一，不再分 cron.xml 和 event-rules.xml）
│   └── sessions/       # 执行会话记录
│       ├── rule_001_1711238400/
│       └── rule_002_1711238500/
├── history/            # 主会话差量文件
└── ...
```

### 文件格式

**sources.xml**：
```xml
<?xml version="1.0" encoding="UTF-8"?>
<EventSources>
    <!-- clock 事件源无需配置，系统自动内建 -->
    <source id="sensor_001" name="设备传感器" type="mqtt"
            endpoint="mqtt://localhost:1883" topic="sensors/device01"
            format="json" />
</EventSources>
```

**rules.xml**：
```xml
<?xml version="1.0" encoding="UTF-8"?>
<Rules>
    <!-- 时间驱动规则 -->
    <rule id="rule_001" name="每日天气汇报"
          enabled="true" source-id="clock"
          message="请汇报今天的天气情况"
          timeout-seconds="300"
          last-run-at-ms="1711152000000" last-status="ok">
        <condition field="time" op="cron-match" value="0 8 * * *" />
    </rule>
    
    <!-- 事件驱动规则（含条件嵌套） -->
    <rule id="rule_002" name="高温异常报警"
          enabled="true" source-id="sensor_001"
          match="all" capture-pre-seconds="5"
          message="检测到异常，请检查设备状态"
          timeout-seconds="300">
        <condition field="temperature" op="gt" value="85" />
        <group match="any">
            <condition field="vibration" op="gt" value="0.2" duration-seconds="3" />
            <condition field="pressure" op="gt" value="100" />
        </group>
    </rule>
</Rules>
```

### 原子写入策略

```
1. 写入临时文件: automation/rules.xml.tmp
2. fsync 确保落盘
3. 重命名: rules.xml.tmp → rules.xml
4. 重命名是原子操作，保证不会出现损坏的中间状态
```

## 场景示例

### 示例1：纯时间触发

**场景**：每天早上8点汇报天气

**用户输入**：
> 每天早上8点汇报天气

**LLM 调用 Rule 工具**：
```json
{
  "action": "add",
  "name": "每日天气汇报",
  "source_id": "clock",
  "conditions": [
    {"field": "time", "op": "cron-match", "value": "0 8 * * *"}
  ],
  "message": "请汇报今天的天气情况"
}
```

**生成的规则 XML**：
```xml
<rule id="rule_001" name="每日天气汇报" source-id="clock"
      message="请汇报今天的天气情况" timeout-seconds="300">
    <condition field="time" op="cron-match" value="0 8 * * *" />
</rule>
```

### 示例2：事件触发 + 条件嵌套

**场景**：当温度超过85度，且（振动值连续3秒高于0.2g **或** 压力超过100）时，触发报警并记录前5秒数据

这是一个典型的混合 AND/OR 条件：`temperature > 85 AND (vibration > 0.2持续3秒 OR pressure > 100)`

**用户输入**：
> 帮我设置一个报警规则：当温度超过85度，同时振动值连续3秒超过0.2g 或者 压力超过100时，触发报警，并保留触发前5秒的数据

**LLM 调用 Rule 工具**：
```json
{
  "action": "add",
  "name": "高温异常报警",
  "source_id": "sensor_001",
  "match": "all",
  "capture_pre_seconds": 5,
  "conditions": [
    {"field": "temperature", "op": "gt", "value": "85"}
  ],
  "groups": [
    {
      "match": "any",
      "conditions": [
        {"field": "vibration", "op": "gt", "value": "0.2", "duration_seconds": 3},
        {"field": "pressure", "op": "gt", "value": "100"}
      ]
    }
  ],
  "message": "检测到异常，请检查设备状态"
}
```

**生成的规则 XML**：
```xml
<rule id="rule_002" name="高温异常报警" source-id="sensor_001"
      match="all" capture-pre-seconds="5"
      message="检测到异常，请检查设备状态" timeout-seconds="300">
    <condition field="temperature" op="gt" value="85" />
    <group match="any">
        <condition field="vibration" op="gt" value="0.2" duration-seconds="3" />
        <condition field="pressure" op="gt" value="100" />
    </group>
</rule>
```

**关键说明**：
- 顶层 `match="all"` 表示 temperature 条件与 group 之间是 AND 关系
- `<group match="any">` 内部的两个条件是 OR 关系
- 这展示了 condition/group 分离设计的优势：LLM 可以直接将自然语言的 AND/OR 组合映射为 XML 结构

### 示例3：时间+数据混合（统一模型的杀手级优势）

**场景**：工作日8-18点期间温度超过85度时报警

这个场景展示了统一模型的核心优势——**时间条件和数据条件可以自由组合**。

**用户输入**：
> 帮我设置一个规则：在工作日8点到18点期间，如果温度超过85度就报警

**LLM 调用 Rule 工具**：
```json
{
  "action": "add",
  "name": "工作时段高温报警",
  "source_id": "sensor_001",
  "match": "all",
  "conditions": [
    {"field": "time", "op": "cron-match", "value": "* 8-18 * * 1-5"},
    {"field": "temperature", "op": "gt", "value": "85"}
  ],
  "message": "工作时段检测到高温异常"
}
```

**生成的规则 XML**：
```xml
<rule id="rule_003" name="工作时段高温报警" source-id="sensor_001"
      match="all" message="工作时段检测到高温异常" timeout-seconds="300">
    <condition field="time" op="cron-match" value="* 8-18 * * 1-5" />
    <condition field="temperature" op="gt" value="85" />
</rule>
```

**关键说明**：
- `source-id` 是 `sensor_001` 而非 `clock`，因为实际数据来自传感器
- `cron-match` 条件在这里充当**时间过滤器**
- 只有在工作日 8-18 点期间收到的传感器数据才参与评估
- 这展示了混合条件的能力，原来分离的两个子系统无法优雅表达这种场景

### 启动流程

```rust
// app/src/main.rs
#[tokio::main]
async fn main() {
    // 初始化 Registry
    let registry = Registry::init().await;
    
    // 创建共享执行器
    let executor = Arc::new(Executor::new(&registry));
    
    // 启动统一规则引擎
    let (rule_tx, rule_handle) = RuleEngine::start(executor.clone()).await;
    
    // 注册工具
    registry.register_tool(RuleTool::new(rule_tx.clone()));
    
    // 运行主循环
    run(&registry).await;
    
    // 关闭
    rule_tx.send(RuleCommand::Shutdown).await.ok();
    rule_handle.await.ok();
}
```

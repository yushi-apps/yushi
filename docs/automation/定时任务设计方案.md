# 自动化任务设计方案

## 目标

基于可逆计算原理，为 Yushi Agent 系统添加自动化执行能力。通过统一的规则引擎（RuleEngine）支持两种触发方式：

1. **时间驱动**：基于 cron 表达式的周期性任务（如"每天早上8点汇报天气"）
2. **事件驱动**：基于外部数据流的条件触发（如"温度超过85度时报警"）

核心洞察：**时间本身就是一种事件源**。将"时钟"视为内建事件源，cron 表达式就只是对时间字段的条件匹配操作符（`cron-match`）。

## 核心概念

### 事件源（EventSource）

事件源定义数据的来源。系统内建 `clock` 时钟事件源，用户可配置外部数据源：

```xml
<EventSources xmlns:x="/nop/schema/xdsl.xdef">
    <!-- 内建：系统自动注册，不需要用户配置 -->
    <source id="clock" name="系统时钟" type="internal" />
    
    <!-- 用户配置的外部数据源 -->
    <source id="string" name="string" type="enum::mqtt,http,file,internal"
            endpoint="string" topic="string" format="enum::json,csv,text"
            poll-interval-ms="!long" />
</EventSources>
```

**属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| id | string | 事件源唯一标识 |
| name | string | 事件源名称 |
| type | enum | 类型：mqtt/http/file/internal |
| endpoint | string | 连接端点（MQTT broker/HTTP URL/文件路径） |
| topic | string | 主题（MQTT topic/HTTP path） |
| format | enum | 数据格式：json/csv/text |
| poll-interval-ms | !long | 轮询间隔（HTTP/file 类型使用） |

### 规则（Rule）

规则是统一的触发单元，同时表达定时任务和事件触发。采用**属性优先**的最小信息表达：

```xml
<Rules xmlns:x="/nop/schema/xdsl.xdef">
    <rule id="string" name="string" description="string"
          enabled="boolean" source-id="string"
          match="enum::all,any"
          capture-pre-seconds="int"
          message="string" timeout-seconds="int"
          delivery-channel="enum::stdout,file,none" delivery-target="string"
          last-run-at-ms="!long" last-status="enum::ok,error,skipped" last-error="string">
        <condition field="string" op="enum::gt,lt,gte,lte,eq,ne,contains,cron-match"
                   value="string" duration-seconds="int" />
        <!-- group: 逻辑组合器，支持递归嵌套（推荐深度 ≤ 2-3 层） -->
        <group match="enum::all,any">
            <condition />  <!-- 引用上面的 condition 定义 -->
            <group />      <!-- 递归嵌套 -->
        </group>
    </rule>
</Rules>
```

**规则属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| id | string | 规则唯一标识 |
| name | string | 规则名称 |
| description | string | 规则描述 |
| enabled | boolean | 是否启用 |
| source-id | string | 关联的事件源 ID（clock 表示时间驱动） |
| match | enum | 顶层条件匹配模式：all（AND）/any（OR），控制顶层 condition 和 group 之间的逻辑关系 |
| capture-pre-seconds | int | 触发时捕获前 N 秒的数据 |
| message | string | 触发执行的消息/指令 |
| timeout-seconds | int | 执行超时秒数 |
| delivery-channel | enum | 交付通道：stdout（标准输出日志）/file（写入指定文件）/none（不交付），默认 none |
| delivery-target | string | 交付目标，根据 channel 类型解释 |
| last-run-at-ms | !long | 上次执行时间戳 |
| last-status | enum | 上次执行状态 |
| last-error | string | 上次错误信息 |
| plan | string | 可选。引用的 task.xml 路径（相对于 automation/ 目录） |

#### Delivery（执行结果交付）

规则可选配置 delivery，指定执行结果的交付方式：

```xml
<rule id="rule_001" name="每日天气汇报" source-id="clock"
      message="请汇报今天的天气情况"
      delivery-channel="stdout"
      delivery-target="">
    <condition field="time" op="cron-match" value="0 8 * * *" />
</rule>
```

| 属性 | 说明 | 默认值 |
|------|------|--------|
| delivery-channel | 交付通道：stdout（标准输出日志）、file（写入指定文件）、none（不交付） | none |
| delivery-target | 交付目标，根据 channel 类型解释 | 空 |

如果未配置 delivery 或 `delivery-channel="none"`，执行结果仅记录在执行日志中，用户可通过 RuleTool 的 `status`/`runs` 操作查询。

**条件属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| field | string | 数据字段路径（如 `temperature`、`time`） |
| op | enum | 操作符：gt/lt/gte/lte/eq/ne/contains/cron-match |
| value | string | 比较值（cron-match 时为 cron 表达式） |
| duration-seconds | int | 持续时间要求：条件必须连续满足指定秒数才算成立 |

**条件组属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| match | enum | 组内条件匹配模式：all（AND）/any（OR） |

> **设计说明**：`<group>` 是逻辑组合器，可包含 `<condition>` 和嵌套的 `<group>`。推荐嵌套深度不超过 2-3 层，实际场景几乎不需要更深的嵌套。

**关键设计**：

- `cron-match` 是专用于时间匹配的操作符，value 为标准 cron 表达式
- `source-id="clock"` + `op="cron-match"` = 纯时间驱动规则
- 非 clock 源 + `op="cron-match"` = 时间过滤器（混合条件）
- 只有 `<condition>` 列表和 `<group>` 用子元素（因为数量不定），其他均为属性
- `<group>` 支持条件嵌套，可表达任意复杂的 AND/OR 组合逻辑

**LLM 友好性设计**：

条件模型的设计优先考虑 LLM 的理解和生成能力，这是区别于传统规则引擎（如 Nop rule.xdef）的核心优势：

| 设计选择 | 说明 |
|---------|------|
| **清晰的语义分离** | `<condition>` 是叶子谓词（判断），`<group>` 是逻辑组合器（AND/OR）。语义明确，LLM 无需学习复杂的递归决策树结构 |
| **零学习成本** | 自然语言描述直接映射：`"温度>85 且 (振动>0.2 或 压力>100)"` → 一个 condition + 一个 any group |
| **扁平优先** | 简单场景（纯 AND 或纯 OR）保持平面结构，rule 的 match 属性作为顶层逻辑，向后兼容 |
| **深度限制** | 推荐嵌套深度 ≤ 2-3 层。实际业务场景几乎不需要更深的嵌套，过深的嵌套反而说明规则需要拆分 |

**对比 Nop 式递归决策树**：Nop 的 rule.xdef 使用统一的递归 `<children>` 结构表达决策树，虽然理论上更通用，但对 LLM 不友好——需要理解"节点既是条件又是组合器"的复杂语义。Yushi 的 condition/group 分离设计牺牲了一点点通用性，换取了显著的 LLM 可用性。

### 执行器（Executor）

执行器是规则触发后的执行基础设施，负责调用 `jieyusha::chat()` 执行 LLM 驱动的任务：

```rust
/// 任务执行请求
struct ExecutionRequest {
    /// 执行来源标识（用于生成 session 目录）
    source_id: String,
    /// 要执行的消息/指令
    message: String,
    /// 超时秒数
    timeout_seconds: u32,
    /// 附加上下文（事件数据、触发时间等）
    context: Option<String>,
}

/// 任务执行结果
struct ExecutionResult {
    status: ExecutionStatus,  // ok | error | timeout
    error: Option<String>,
    started_at: i64,
    finished_at: i64,
}
```

执行器的职责：
- 使用共享的 history 目录：`automation/sessions/{rule_id}/`（同一规则的所有 LLM 执行共用）
- 调用 `jieyusha::chat_stream()` 执行 message
- 超时控制
- **记录执行日志（JSONL 格式）**
- **按 delivery 配置交付执行结果**

#### 执行日志

每条规则的执行记录以 JSON Lines 格式追加写入 `automation/sessions/runs/{rule_id}.jsonl`，每行一条记录：

```json
{"ts":1711234567890,"rule_id":"rule_001","status":"ok","source":"plan","started_at_ms":1711234567000,"finished_at_ms":1711234567890,"duration_ms":890}
{"ts":1711234568000,"rule_id":"rule_001","status":"error","source":"llm","error":"LLM timeout","started_at_ms":1711234568000,"finished_at_ms":1711234598000,"duration_ms":30000}
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| ts | i64 | 记录写入时间戳（ms） |
| rule_id | string | 规则 ID |
| status | enum | 执行状态：ok / error / timeout |
| source | enum | 执行来源：plan（重放 plan）/ llm（LLM 执行） |
| error | string | 错误信息（仅 error/timeout 时存在） |
| started_at_ms | i64 | 执行开始时间 |
| finished_at_ms | i64 | 执行结束时间 |
| duration_ms | i64 | 执行耗时 |

### 隔离执行与共享会话目录

自动化任务在**独立的 Agent 会话**中执行，不干扰主会话。**同一规则的所有执行共用一个会话目录** `sessions/{rule_id}/`，每次 LLM 执行在该目录下追加 history 差量文件：

```
┌─────────────────────────────────────────────────────────┐
│                    主会话 (Main Session)                 │
│  history/                                               │
│  ├── 0_workspace.xml                                    │
│  ├── 1_intent.xml     ← x:extends="0_workspace.xml"    │
│  └── ...                                                │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│             自动化任务共享会话 (Automation Session)        │
│  automation/sessions/{rule_id}/                         │
│  ├── 0_workspace.xml      ← 基于主会话的精简 workspace   │
│  │                                                      │
│  │  ══════ 首次 LLM 执行 ══════                         │
│  ├── 1_intent.xml         ← x:extends="0_workspace.xml" │
│  ├── 2_thought.xml        ← x:extends="1_intent.xml"    │
│  ├── 3_toolcall.xml       ← x:extends="2_thought.xml"   │
│  ├── 4_summary.xml        ← x:extends="3_toolcall.xml"  │
│  │                                                      │
│  │  ══════ Plan 失效后 LLM 回退执行 ══════               │
│  ├── 5_intent.xml         ← x:extends="4_summary.xml"   │
│  ├── 6_thought.xml        ← x:extends="5_intent.xml"    │
│  ├── 7_toolcall.xml       ← x:extends="6_thought.xml"   │
│  ├── 8_summary.xml        ← x:extends="7_toolcall.xml"  │
│  └── ...                                                │
└─────────────────────────────────────────────────────────┘
```

**共享会话目录的核心价值**：当 plan 失效需要 LLM 回退执行时，LLM 能看到前次成功的 history 差量链（intent → thought → toolcall → summary），从而继承成功模式、提高回退执行的准确率。

**会话差量链文件说明**：

| 文件 | 内容 | x:extends |
|------|------|----------|
| 0_workspace.xml | 初始 workspace（包含 agent 定义、tools 等） | 无（链头） |
| N_intent.xml | 规则的 message 作为 intent | 前一个文件 |
| N+1_thought.xml | LLM 思考过程 | N_intent.xml |
| N+2_toolcall.xml | 工具调用记录 | N+1_thought.xml |
| N+3_summary.xml | 工具执行结果 | N+2_toolcall.xml |

## Plan 缓存机制

### 设计动机

当前定时任务系统中，每次规则触发都调用 LLM 执行。对于固定规则的重复任务，这带来三个问题：

1. **资源浪费**：每次触发都消耗 LLM 推理资源，即使任务逻辑完全相同
2. **执行不稳定**：LLM 的非确定性可能导致相同输入产生不同的工具调用序列
3. **响应延迟**：LLM 推理引入额外的延迟，影响任务执行效率

**核心洞察**：对于固定规则的重复任务（如"每天8点查天气"），LLM 首次执行后的工具调用序列是**可复用的执行经验**。

**决策**：引入 **plan 缓存机制**——LLM 首次执行后自动提取工具调用序列为 task.xml，后续直接重放，失败时回退 LLM 重新推导。

## 可逆计算视角下的 Plan 定位

从可逆计算原理 `Y = F(X) + Delta` 的视角理解 plan 缓存：

| 概念 | 含义 |
|------|------|
| X | Rule 的 message（触发指令） |
| F | LLM 执行函数（chat_stream） |
| Y | 执行结果（工具调用序列 + 输出） |
| Delta | task.xml（LLM 的执行经验） |

**执行策略**：
- **首次执行**：`Y = F(X)`，LLM 推理生成工具调用序列，同时提取为 Delta（task.xml）
- **后续执行**：`Y = Delta`，直接重放 task.xml 中的工具调用序列
- **失败回退**：重放失败时，清空 Delta，回退到 `Y = F(X)` 重新推导

这种设计使 plan 成为**附着在 Rule 上的执行经验差量**，与整个系统的差量计算架构保持一致。

### Plan 提取的可逆计算基础

Plan 提取本质是对 history 差量链执行 merge 操作后，从合并结果中提取 toolcall 节点：

```
Plan 提取 = merge(history 差量链) → 提取 toolcall 节点
```

#### Merge 引擎的 Key 属性匹配

XDSL merge 引擎（`tuo::xdsl::merge`）已支持**基于 key 属性的节点匹配**：

| 匹配优先级 | key 属性 | 说明 |
|-----------|----------|------|
| 1 | `id` | 最高优先级，唯一标识 |
| 2 | `name` | 次优先级 |
| 3 | `key` | 通用 key 属性 |
| 4 | tag_name | 无 key 属性时退化为 tag 匹配（向后兼容） |

匹配规则：
- 合并子节点时，使用 key 属性（id/name/key）判断同 tag 节点是否为"同一节点"
- 双方都有同一 key 属性时，值必须相等才视为同一节点
- 匹配成功的节点进行递归合并；未匹配的新节点追加到结果中

#### Toolcall ID 的语义与重试复用

History 差量链中每个 toolcall 都有 `id` 属性。当 LLM 回退执行时，toolcall id 有特殊的**重试复用语义**：

1. **正常执行**：toolcall 使用递增序号作为 id（如 `tc_1`, `tc_2`...）
2. **重试执行**：检查 history 中是否存在同工具名 + `status="failed"` 的 toolcall
   - 若存在：复用失败 toolcall 的 id
   - 若不存在：使用新的递增序号

**核心价值**：merge 时，新的成功 toolcall 会**自然覆盖**同 id 的失败记录，无需手动清理。

```xml
<!-- 首次执行失败 -->
<toolcall id="tc_3" tool="bash" status="failed">
    <arguments>{"command":"curl weather.api"}</arguments>
    <error>Connection timeout</error>
</toolcall>

<!-- 重试执行成功，复用 id="tc_3" -->
<toolcall id="tc_3" tool="bash" status="success">
    <arguments>{"command":"curl weather.api"}</arguments>
    <result>...</result>
</toolcall>

<!-- merge 后：失败记录被成功记录覆盖 -->
```

这使得 Plan 提取时只会看到最终的成功 toolcall 序列，失败的中间尝试被自动消除。

### task.xml 格式定义

Plan 以独立的 task.xml 文件存储，采用简化的步骤序列格式：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<task xmlns:x="/nop/schema/xdsl.xdef" 
      source-session="sessions/rule_001"
      created-at-ms="1774334280000">
    <step tool="bash" 
          arguments='{"command":"curl -s \"wttr.in/?format=%t\" | tr -d \"+\" | sed \"s/°C//\""}' />
    <step tool="bash" 
          arguments='{"command":"echo \"当前温度: $RESULT\""}' />
</task>
```

**task 根元素属性**：

| 属性 | 类型 | 说明 |
|------|------|------|
| source-session | string | 生成此 plan 的原始会话路径 |
| created-at-ms | !long | plan 创建时间戳 |

**step 元素属性**：

| 属性 | 类型 | 说明 |
|------|------|------|
| tool | string | 工具名称 |
| arguments | string | 工具参数（JSON 格式） |

> **设计简化**：与 Nop 的完整 task.xdef（支持并行、循环、条件分支等复杂流程）不同，Yushi 的 task.xml 采用极简的线性步骤序列。这是因为 LLM 生成的工具调用本身就是线性的 thought → toolcall → summary 序列，复杂流程控制应由 LLM 在运行时决策，而非固化在 plan 中。

### 文件存储结构

```
automation/
├── rules/              # 规则差量链
│   ├── 0_base.xml
│   ├── 1_add_rule_001.xml
│   └── ...
├── plans/              # LLM 自动提取的执行计划
│   ├── rule_001.task.xml    # rule_001 的缓存 plan
│   └── rule_002.task.xml    # rule_002 的缓存 plan
└── sessions/           # 执行会话目录（每个规则共用一个目录）
    ├── runs/           # JSONL 执行日志
    │   └── rule_001.jsonl
    └── rule_001/       # rule_001 的共享会话目录（差量链持续追加）
        ├── 0_workspace.xml
        ├── 1_intent.xml      # 首次执行
        ├── 2_thought.xml
        ├── 3_toolcall.xml
        ├── 4_summary.xml
        ├── 5_intent.xml      # 回退执行（plan 失效时）
        ├── 6_thought.xml
        └── ...
```

**命名约定**：
- plan 文件名：`{rule_id}.task.xml`
- plan 与 rule 一一对应，通过 rule_id 关联

### Rule 引用 Plan

Rule 通过可选的 `plan` 属性引用 task.xml 文件：

```xml
<rule id="rule_001" name="每日天气汇报" source-id="clock"
      message="请汇报今天的天气情况"
      plan="plans/rule_001.task.xml"
      timeout-seconds="300">
    <condition field="time" op="cron-match" value="0 8 * * *" />
</rule>
```

**plan 属性说明**：

| 属性 | 类型 | 说明 |
|------|------|------|
| plan | string | 可选。指向 task.xml 的相对路径（相对于 automation/ 目录） |

**行为语义**：
- `plan` 属性存在且文件存在：执行时优先重放 plan
- `plan` 属性不存在或文件不存在：执行时调用 LLM
- plan 重放失败：清空 plan 文件，回退 LLM 重新执行

### 执行流程（两层优化机制）

系统采用**两层优化机制**配合工作：Plan 重放（第一层）消除重复 LLM 调用，共享会话目录（第二层）在 LLM 回退时提供历史上下文。

**完整执行流程**：

```
触发 → 检查 plan 缓存
├─ 存在 → 重放 plan
│  ├─ 成功 → deliver 原始输出（source=plan）
│  └─ 失败 → 删除 plan → 回退 LLM ↓
└─ 不存在 → LLM 执行（chat_stream）
   ├─ 成功 → 提取并保存 plan → deliver（source=llm）
   └─ 失败 → 记录错误（source=llm）
```

**详细流程说明**：

```
规则触发
├── 有 plan（task.xml）?
│   ├── 是 → 直接重放工具调用序列
│   │   │     （不经过 chat_stream，不接触 session 目录）
│   │   │     通过 Registry::get_tool() 查找工具后直接 tool.call()
│   │   ├── 成功 → 写 JSONL 日志（source: plan）→ 完成
│   │   └── 失败 → 清空 plan → 进入"无 plan"分支 ↓
│   └── 否 → 调用 chat_stream，使用 sessions/{rule_id}/ 共享目录
│           │     LLM 能看到前次的 history 差量链
│           ├── 成功 → 提取 toolcall → 保存为 task.xml → 写 JSONL（source: llm）
│           └── 失败 → 写 JSONL（status: error, source: llm）
```

#### 两层优化机制对比

| | Plan 重放（第一层） | 共享会话目录（第二层） |
|---|---|---|
| **何时生效** | plan 存在时（常态） | plan 不存在或失败时（首次或回退） |
| **是否调用 LLM** | 否 | 是 |
| **是否使用 session 目录** | 否 | 是 |
| **解决什么问题** | 消除重复 LLM 调用（快、稳、省） | LLM 回退时提供历史上下文（更准） |

#### History 链演进示例

以规则 `rule_001`（每日天气汇报）的完整生命周期为例：

**首次触发**（无 plan，无 history）：
```
sessions/rule_001/
├── 0_workspace.xml
├── 1_intent.xml        ← "请汇报今天的天气情况"
├── 2_thought.xml       ← LLM 分析任务
├── 3_toolcall.xml      ← 调用 bash 获取天气
└── 4_summary.xml       ← 执行结果

→ 成功 → 提取 toolcall → 生成 plans/rule_001.task.xml
```

**第 2~N 次触发**（plan 存在）：
```
→ 直接重放 task.xml 中的工具调用序列
→ session 目录不被触碰，history 链保持不变
→ 写 JSONL 日志（source: plan）
```

**Plan 失败回退**（如工具参数过期）：
```
→ plan 重放失败 → 清空 plan → LLM 在共享目录执行

sessions/rule_001/
├── 0_workspace.xml
├── 1_intent.xml        ← 首次执行的 intent
├── 2_thought.xml       ← 首次执行的 thought
├── 3_toolcall.xml      ← 首次执行的 toolcall（LLM 可参考）
├── 4_summary.xml       ← 首次执行的 summary
├── 5_intent.xml        ← 回退执行的 intent（同样的 message）
├── 6_thought.xml       ← LLM 参考前次 toolcall，大概率复用成功命令
├── 7_toolcall.xml      ← 新的工具调用
└── 8_summary.xml       ← 执行结果

→ 成功 → 提取新 toolcall → 生成新的 plans/rule_001.task.xml
```

### Plan 生命周期

#### 创建（Create）

LLM 首次成功执行后，自动从 session history 差量文件中提取 toolcall 序列生成 task.xml：

**触发条件**：LLM 执行成功（`ExecutionStatus::Ok`）时自动触发 plan 提取

**提取流程**：

1. **合并差量链**：调用 `jieyusha::memory::get_merged_memory_xml()` 合并 session 目录下的所有 history 差量文件
   - 内部使用 `tuo::xdsl::merge` 执行递归合并
   - merge 使用 key 属性匹配（id > name > key）识别同一节点
   - 重试的 toolcall 因 id 复用而自动覆盖失败记录
2. **提取 toolcall**：从合并结果中提取 `status="success"` 的 toolcall 节点
3. **生成 step 序列**：提取每个 toolcall 的 `name`（工具名）和 `arguments`（参数），按顺序组装为 `<step>` 序列
4. **写入 plan 文件**：调用 `storage.save_plan()` 写入 `plans/{rule_id}.task.xml`

**失败处理**：plan 提取过程中的任何错误（合并失败、解析失败、无成功 toolcall）仅记录警告日志，不影响 LLM 执行结果的返回

```
sessions/rule_001/
├── 0_workspace.xml
├── 1_intent.xml
├── 2_thought.xml
├── 3_toolcall.xml    ──────┐
├── 4_thought.xml           │  提取
├── 5_toolcall.xml    ──────┼────────►  plans/rule_001.task.xml
└── 6_summary.xml           │
```

#### 使用（Use）

后续触发时直接重放 task.xml 中的步骤：

**执行路径**：plan 重放**绕过 LLM**，直接通过工具注册表执行工具调用

1. 调用 `storage.read_plan()` 读取并解析 `plans/{rule_id}.task.xml`
2. 遍历每个 `<step>`，通过 `Registry::get_tool()` 查找工具
3. 解析 step 的 arguments JSON，构建 `ToolUseContext`
4. 直接调用 `tool.call()` 执行工具
5. 收集每个 step 的原始工具输出
6. 记录执行日志，`source` 字段标记为 `"plan"`

**重放优势**：
- **快速**：无 LLM 推理延迟
- **确定**：每次执行完全相同的工具调用序列
- **经济**：不消耗 LLM 推理资源
- **不触碰 session 目录**：plan 重放期间不写入任何 history 文件

#### 失效（Invalidate）

重放失败时立即终止并回退 LLM 重新执行：

**失败判定条件**：
- 工具调用返回错误（`is_error = true`）
- 工具不存在（`Registry::get_tool()` 返回 `None`）
- 参数解析失败（JSON 解析错误）
- 执行超时

**失败处理策略**：**立即终止重放 + 删除 plan 文件 + 回退 LLM 执行**

1. 检测到任意 step 失败后，立即终止后续 step 的执行
2. 调用 `storage.clear_plan()` 删除 `plans/{rule_id}.task.xml` 文件
3. 回退到 LLM 执行路径，调用 `jieyusha::chat_stream()` 重新推导
4. 回退后的 LLM 执行日志 `source` 字段标记为 `"llm"`
5. LLM 执行成功后会重新提取并保存新的 plan

**回退执行的优势**：LLM 回退执行时使用共享会话目录 `sessions/{rule_id}/`，能看到前次成功执行的 history 差量链，大概率复用成功的工具调用模式。

#### 规则更新时的 plan 失效

当通过 RuleTool 的 `update` 操作变更规则的 `message` 字段时，系统自动清空对应的 plan 缓存文件：

**触发条件**：
- 仅当 `message` 字段变更时触发 plan 清空
- 其他字段变更（name、description、timeout、delivery 等）不影响 plan 有效性

**处理逻辑**：
1. RuleTool 的 `update` 操作成功后检查 patch 是否包含 `message` 变更
2. 若包含，调用 `storage.clear_plan(rule_id)` 删除对应的 plan 文件
3. 清空失败仅记录警告日志，不阻断 update 操作

**效果**：
- 下次触发时无 plan 可用，回退 LLM 重新执行

## Rule 到 `task.xdef` 的兼容与迁移方案

为了与 `tuo/xdefs/task.xdef` 深度融合，建议建立一套从 Rule 定义到 Plan 的映射流程，实现高质量迁移：

1. **Rule 仍保留触发引擎**
   - `RuleEngine` 继续评估 `source-id`, `condition`, `group` 等触发条件
   - 触发后构建 `ExecutionRequest`，如果 plan 存在则重放，否则进入 LLM 执行

2. **Plan 结构由 `task.xdef` 取代现有 step 列表**
   - 目前 `plans/{rule_id}.task.xml` 的简化格式可过渡到正式 `task.xdef`：
     - `<task name="rule_{id}" ...>`
     - `<sequence> ... <call-tool tool="..." .../> ...</sequence>`
   - 视图级别 `task.xdef` 可以支持后续并行/分支/重试、graph 等扩展

3. **Plan 提取升级为 `task.xdef` 生成**
   - 在 `Executor::extract_and_save_plan` 中：
     - 合并历史差量 → 提取 `success` toolcall
     - 构建 `task` 文档包含 `sequence` + `call-tool`
     - 写入 `storage.save_plan` 为 `plans/{rule_id}.task.xml`

4. **重放逻辑从 `replay_plan` 迁移到 `replay_task`**
   - `Executor::execute`：
     - 有 `task.xml` → 直接调用 `replay_task(task)`
     - 失败（工具缺失/参数解析/工具执行失败）→ `storage.clear_plan` + LLM 回退

5. **Rule 更新自动失效映射**
   - 规则的 `message`、`plan` 引用变更、`source-id` 变更应清除对应 `task.xml`，避免语义不一致
   -  `RuleTool` 额外日志记录 `plan_version`、`rule_hash` 对比，便于审计

6. **兼容双模式（渐进发布）**
   - 先保留现有 `PlanStep` 和 `task.xdef` 双写：即当提取 plan 时同步生成 `task.xdef`，并继续维持旧 plan 与新 plan 并行可用
   - `RuleEngine` 逐步切换优先级为 `task.xdef < PlanStep`](较新版本，向前兼容)

### 迁移好处
- 将“规则触发 + LLM 工具调用序列”流水线化为可执行任务定义，更易于调度、重试、监控
- 减少自动化系统对 LLM 的依赖，增强确定性和效率
- `task.xdef` 原生支持图形/并行/重试/超时，可在未来无缝扩展复杂任务

### 举例：Rule 到 task.xdef 模板

```xml
<task name="rule_rule_001" version="1" created-at-ms="..." record-metrics="true">
  <sequence name="main">
    <call-tool name="step1" tool="Bash" timeout="30000">
      <input name="arguments" type="string"><source value='{"cmd":"echo \'HELLO\'"}'/></input>
    </call-tool>
    <call-tool name="step2" tool="CustomTool" timeout="60000">
      <input name="arguments" type="string"><source value='{"arg1":42}'/></input>
    </call-tool>
  </sequence>
</task>
```

- 日后如果需要分支可改成 `<if>` 或 `<selector>`，不影响 Rule 引擎触发逻辑。

---

> 结论：在现有自动化架构上添加 `task.xdef` 迁移，是一条高质量的路径。它既保护现有 Rule 触发能力，又逐步让执行语义转到可编排任务模型，适合生产环境逐步灰度 roll out。
- LLM 根据新 message 生成新的工具调用序列
- 执行成功后生成新的 plan 缓存

**设计考量**：
- Plan 是从旧 message 的 LLM 执行中提取的工具调用序列
- message 变更意味着任务意图改变，旧 plan 与新意图不匹配
- 清空 plan 强制系统重新通过 LLM 推导正确的执行方案

#### 更新（Update）

LLM 重新成功执行后，覆盖生成新的 task.xml：

- 当 plan 失效后 LLM 重新执行成功，会重新生成 plan
- 新 plan 覆盖旧 plan（如果存在）
- 更新 `created-at-ms` 和 `source-session` 属性

1. **History 链增长控制**：plan 覆盖绝大多数执行（直接重放不写 history），LLM 回退执行极少发生，因此 history 链增长缓慢。即使长期运行，单个规则的 session 目录也不会膨胀过大。

## RuleEngine 设计

### 架构概览

RuleEngine 是统一的规则引擎，整合了时间驱动和事件驱动的触发能力：

```
EventSources（含内建 clock）
       │
       │  数据流
       ▼
  RuleEngine（统一）
   ├── 条件匹配器（含 cron-match 操作符）
   ├── 窗口评估器（滑动窗口 + 持续时间）
   └── 环形缓冲区（回溯数据）
       │
       │  触发
       ▼
   Executor → jieyusha::chat()
```

#### 并发执行保护

RuleEngine 为每条规则维护 `running_rules` 标记集合，防止同一规则被重复触发：

- **时钟/事件触发**：如果规则正在执行，静默跳过本次触发（记录 debug 日志）
- **手动触发（run）**：如果规则正在执行，返回错误信息“Rule {id} is already running”

这确保同一规则在任意时刻最多只有一个执行实例。

### cron-match 优化

对于 `source-id="clock"` 的规则，不能每秒触发规则评估（太浪费）。RuleEngine 采用**预计算下次匹配时间**的优化策略：

```rust
/// 时钟规则的下次触发时间
struct ClockRuleState {
    rule_id: String,
    next_match_at_ms: i64,  // 预计算的下次匹配时间
}
```

优化策略：
1. 对于 `source-id="clock"` 的规则，解析 cron 表达式预计算下次匹配时间
2. 使用单定时器 sleep 到最近的下次匹配时间
3. 触发后重新计算下次匹配时间
4. 对于非 clock 源，才是实时数据流评估

### 核心循环

```rust
/// RuleEngine 命令
enum RuleCommand {
    Add(Rule),
    Update(String, RulePatch),
    Remove(String),
    RunNow(String),
    Shutdown,
}

/// RuleEngine 核心循环
loop {
    tokio::select! {
        // 分支1：时钟规则到期
        _ = sleep_until(next_clock_wake) => {
            execute_due_clock_rules().await;
            recompute_next_clock_wake();
        }
        // 分支2：收到外部事件数据
        Some(event) = event_rx.recv() => {
            evaluate_event_rules(&event).await;
        }
        // 分支3：收到管理命令
        Some(cmd) = command_rx.recv() => {
            handle_command(cmd).await;
        }
    }
}
```

### 规则评估

```rust
/// 事件数据点
struct EventData {
    source_id: String,
    timestamp_ms: i64,
    fields: HashMap<String, Value>,
}

/// 规则状态机
struct RuleState {
    rule_id: String,
    /// 每个条件的持续满足开始时间
    condition_start_times: Vec<Option<i64>>,
    /// 上次触发时间（用于防抖）
    last_triggered_at: Option<i64>,
}

/// 环形缓冲区
struct RingBuffer {
    data: VecDeque<EventData>,
    max_duration_ms: i64,
}
```

规则评估伪代码：

```rust
fn evaluate_rule(rule: &Rule, data: &EventData, state: &mut RuleState) -> bool {
    let now = data.timestamp_ms;
    let mut satisfied_count = 0;
    
    for (i, cond) in rule.conditions.iter().enumerate() {
        let is_satisfied = match cond.op {
            Op::Gt => data.fields.get(&cond.field) > cond.value,
            Op::Lt => data.fields.get(&cond.field) < cond.value,
            Op::CronMatch => {
                // 对于非 clock 源的 cron-match，检查当前时间是否匹配
                let current_time = Utc::now();
                cron_matches(&cond.value, current_time)
            }
            // ... 其他操作符
        };
        
        if is_satisfied {
            // 记录条件开始满足的时间
            if state.condition_start_times[i].is_none() {
                state.condition_start_times[i] = Some(now);
            }
            
            // 检查是否满足持续时间要求
            if let Some(duration) = cond.duration_seconds {
                let start = state.condition_start_times[i].unwrap();
                if (now - start) >= duration * 1000 {
                    satisfied_count += 1;
                }
            } else {
                satisfied_count += 1;
            }
        } else {
            // 条件不满足，重置计时器
            state.condition_start_times[i] = None;
        }
    }
    
    match rule.match_mode {
        Match::All => satisfied_count == rule.conditions.len(),
        Match::Any => satisfied_count > 0,
    }
}
```

## RuleTool 工具设计

统一的规则管理工具，取代原来的 CronTool + EventRuleTool：

```xml
<tool name="Rule" description="管理自动化规则：创建、查看、更新、删除规则，支持时间驱动和事件驱动"
      input-schema="{...}" />
```

**操作说明**：

| 操作 | 说明 |
|------|------|
| status | 查看引擎状态（规则总数、下次时钟触发时间、活跃事件源数量、**各规则最近一次执行记录**） |
| list | 列出所有规则（从差量链合并得到当前状态） |
| add | 创建规则（生成 `N_add_{rule_id}.xml` 差量文件） |
| update | 更新规则属性（生成 `N_update_{rule_id}.xml` 差量文件，`x:override="merge"`） |
| remove | 删除规则（生成 `N_remove_{rule_id}.xml` 差量文件，`x:override="remove"`） |
| run | 立即触发规则执行（不影响正常调度） |
| list-sources | 列出可用事件源 |

**参数说明**（JSON Schema）：

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| action | enum | 是 | 操作类型：status/list/add/update/remove/run/list-sources |
| id | string | update/remove/run 时必需 | 规则 ID |
| name | string | add 时必需 | 规则名称 |
| description | string | 否 | 规则描述 |
| source_id | string | add 时必需 | 事件源 ID（clock 表示时间驱动） |
| match | enum | 否 | 顶层匹配模式：all/any，默认 all |
| capture_pre_seconds | integer | 否 | 捕获触发前数据的秒数 |
| conditions | array | add 时必需 | 顶层条件列表 |
| groups | array | 否 | 顶层条件组列表（用于混合 AND/OR 逻辑） |
| message | string | add 时必需 | 触发时执行的消息 |
| timeout_seconds | integer | 否 | 超时秒数，默认 300 |
| enabled | boolean | 否 | 是否启用，默认 true |
| delivery_channel | enum | 否 | 交付通道：stdout/file/none，默认 none |
| delivery_target | string | 否 | 交付目标（delivery_channel=file 时为文件路径） |

**conditions 数组元素**：

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| field | string | 是 | 数据字段路径（时间驱动固定为 `time`） |
| op | enum | 是 | 操作符：gt/lt/gte/lte/eq/ne/contains/cron-match |
| value | string | 是 | 比较值（cron-match 时为 cron 表达式） |
| duration_seconds | integer | 否 | 持续时间要求 |

**groups 数组元素**：

| 参数 | 类型 | 必需 | 说明 |
|------|------|------|------|
| match | enum | 是 | 组内匹配模式：all/any |
| conditions | array | 否 | 组内条件列表 |
| groups | array | 否 | 嵌套的条件组（支持递归，推荐深度 ≤ 2-3 层） |

## 持久化存储

### 可逆计算一致性

Yushi 的自动化持久化层遵循 `Y = F(X) + Delta` 原则，与 Memory 系统的差量模式保持一致：

| 概念 | Memory 系统 | 自动化系统 |
|------|-------------|------------|
| 差量链 | `0_workspace.xml → N_intent.xml → N_tool.xml` | `0_base.xml → 1_add_xxx.xml → 2_update_xxx.xml` |
| 链接机制 | `x:extends="前一个文件"` | `x:extends="前一个文件"` |
| 合并策略 | XDSL merge/append/prepend/replace/remove | `x:override="merge/remove"` |
| 当前状态 | `process_extends` 递归合并 | 扫描目录，链式合并得到当前规则集 |

核心优势：
- **可追溯**：每次变更作为独立差量文件存在，完整保留操作历史
- **可回滚**：通过截断差量链即可恢复到任意历史状态
- **合并冲突友好**：增量修改减少协作冲突

### 存储路径

### x:override 合并规则

RuleTool 操作与 XDSL 合并策略的映射关系：

| 操作 | x:override | 语义 |
|------|------------|------|
| add | 无（默认 merge） | 新增子节点，添加到规则集 |
| update | `merge` | 属性覆盖，仅修改指定属性 |
| remove | `remove` | 删除节点，从规则集中移除 |

XDSL 合并引擎（tuo crate 的 `process_extends`）支持的完整合并策略：
- `merge`：默认策略，递归合并子节点
- `append`：追加到同级列表末尾
- `prepend`：插入到同级列表开头
- `replace`：完全替换节点
- `remove`：删除节点

### 差量文件写入策略

```
1. 扫描目录获取当前最大序号 N
2. 生成新文件名: (N+1)_{action}_{rule_id}.xml
3. 写入临时文件: automation/rules/(N+1)_{action}_{rule_id}.xml.tmp
4. fsync 确保落盘
5. 重命名: .xml.tmp → .xml（原子操作）
```

### 启动恢复流程

```
1. 创建 Executor 实例
2. 扫描 automation/rules/ 目录，按序号排序获取文件列表
3. 调用 tuo::xdsl::process_extends() 递归合并差量链
4. 得到当前完整规则集
5. 从执行日志（JSONL）恢复每条规则的状态：
   - 读取 automation/sessions/runs/{rule_id}.jsonl 的最后一条记录
   - 从记录中提取 started_at_ms 作为 last_run_at_ms
   - 从记录中提取 status 转为 last_status
   - 从记录中提取 error 作为 last_error
6. 对每个 clock 规则，计算下次触发时间
7. 启动规则引擎循环
```

> **设计简化**：早期版本使用 `N_state_{rule_id}.xml` 差量文件持久化规则状态，但该信息与执行日志高度重叠。现已统一从执行日志恢复状态，移除了冠余的状态差量机制。

## 场景示例

### 示例1：纯时间触发

**场景**：每天早上8点汇报天气

**用户输入**：
> 每天早上8点汇报天气

**LLM 调用 Rule 工具**：
```json
{
  "action": "add",
  "name": "每日天气汇报",
  "source_id": "clock",
  "conditions": [
    {"field": "time", "op": "cron-match", "value": "0 8 * * *"}
  ],
  "message": "请汇报今天的天气情况"
}
```

**生成的规则 XML**：
```xml
<rule id="rule_001" name="每日天气汇报" source-id="clock"
      message="请汇报今天的天气情况" timeout-seconds="300"
      delivery-channel="none" delivery-target="">
    <condition field="time" op="cron-match" value="0 8 * * *" />
</rule>
```

### 示例2：事件触发 + 条件嵌套

**场景**：当温度超过85度，且（振动值连续3秒高于0.2g **或** 压力超过100）时，触发报警并记录前5秒数据

这是一个典型的混合 AND/OR 条件：`temperature > 85 AND (vibration > 0.2持续3秒 OR pressure > 100)`

**用户输入**：
> 帮我设置一个报警规则：当温度超过85度，同时振动值连续3秒超过0.2g 或者 压力超过100时，触发报警，并保留触发前5秒的数据

**LLM 调用 Rule 工具**：
```json
{
  "action": "add",
  "name": "高温异常报警",
  "source_id": "sensor_001",
  "match": "all",
  "capture_pre_seconds": 5,
  "conditions": [
    {"field": "temperature", "op": "gt", "value": "85"}
  ],
  "groups": [
    {
      "match": "any",
      "conditions": [
        {"field": "vibration", "op": "gt", "value": "0.2", "duration_seconds": 3},
        {"field": "pressure", "op": "gt", "value": "100"}
      ]
    }
  ],
  "message": "检测到异常，请检查设备状态"
}
```

**生成的规则 XML**：
```xml
<rule id="rule_002" name="高温异常报警" source-id="sensor_001"
      match="all" capture-pre-seconds="5"
      message="检测到异常，请检查设备状态" timeout-seconds="300"
      delivery-channel="none" delivery-target="">
    <condition field="temperature" op="gt" value="85" />
    <group match="any">
        <condition field="vibration" op="gt" value="0.2" duration-seconds="3" />
        <condition field="pressure" op="gt" value="100" />
    </group>
</rule>
```

**关键说明**：
- 顶层 `match="all"` 表示 temperature 条件与 group 之间是 AND 关系
- `<group match="any">` 内部的两个条件是 OR 关系
- 这展示了 condition/group 分离设计的优势：LLM 可以直接将自然语言的 AND/OR 组合映射为 XML 结构

### 示例3：时间+数据混合（统一模型的杀手级优势）

**场景**：工作日8-18点期间温度超过85度时报警

这个场景展示了统一模型的核心优势——**时间条件和数据条件可以自由组合**。

**用户输入**：
> 帮我设置一个规则：在工作日8点到18点期间，如果温度超过85度就报警

**LLM 调用 Rule 工具**：
```json
{
  "action": "add",
  "name": "工作时段高温报警",
  "source_id": "sensor_001",
  "match": "all",
  "conditions": [
    {"field": "time", "op": "cron-match", "value": "* 8-18 * * 1-5"},
    {"field": "temperature", "op": "gt", "value": "85"}
  ],
  "message": "工作时段检测到高温异常"
}
```

**生成的规则 XML**：
```xml
<rule id="rule_003" name="工作时段高温报警" source-id="sensor_001"
      match="all" message="工作时段检测到高温异常" timeout-seconds="300"
      delivery-channel="none" delivery-target="">
    <condition field="time" op="cron-match" value="* 8-18 * * 1-5" />
    <condition field="temperature" op="gt" value="85" />
</rule>
```

**关键说明**：
- `source-id` 是 `sensor_001` 而非 `clock`，因为实际数据来自传感器
- `cron-match` 条件在这里充当**时间过滤器**
- 只有在工作日 8-18 点期间收到的传感器数据才参与评估
- 这展示了混合条件的能力，原来分离的两个子系统无法优雅表达这种场景
